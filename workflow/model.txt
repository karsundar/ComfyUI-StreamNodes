# Project: True Streaming Video Pipeline for ComfyUI Wan Animate 2

## 1. Objective

Implement a memory-efficient, end-to-end streaming video pipeline for **ComfyUI Wan Animate 2**, replacing video-processing components that load entire videos into RAM or VRAM.

The primary use case is:

**Reference image + driver video → Wan Animate 2 → generated video with audio**

The solution should support long input videos and high input resolutions, including 1080p, without memory consumption growing proportionally to total video duration.

The implementation must preserve video-generation quality, character consistency, and temporal continuity.

- GPU framework: ROCm
- ComfyUI: Existing working installation

- Existing working model: Wan Animate 2

**Critical constraint:** Do not reinstall or modify PyTorch, ROCm, or the existing ComfyUI environment unnecessarily.

The current native Wan Animate 2 workflow works. Preserve its model-loading, conditioning, sampling, and VAE behavior.

## 4. Problems in the Current Implementation

### Problem A: VideoStreamLoader is not truly streaming

The current implementation uses PyAV to decode frames incrementally but eventually accumulates frames in a Python list and combines them using `torch.stack()`.

This means memory usage increases with the number of decoded frames.

**Required change:**

Implement bounded-memory video decoding.

The loader should process only a configurable window of frames at a time.

Example:

```text
Input video: 1920×1080, 10 minutes

Window 1: frames 0–80
Window 2: frames 73–153
Window 3: frames 146–226
...
```

The exact window boundaries must be determined by the selected overlap and the native Wan Animate 2 continuation mechanism.

Do not assume overlapping windows can simply be concatenated.

### Problem B: GetVideoComponents+ is still used

The converted workflow retains `GetVideoComponents+` for audio and FPS.

Although this node supports lazy decoding, the goal is to eliminate this dependency.

Replace its functionality with:

**VideoStreamMetadata**
- Read video dimensions.
- Read FPS.
- Determine frame count or duration.
- Return metadata without decoding the complete video.

**VideoStreamAudio**
- Preserve the original audio.
- Avoid decoding the complete audio track into a large in-memory tensor.
- Prefer stream-copy or FFmpeg-based muxing where compatible.

### Problem C: CreateVideo is not an incremental output writer

The existing workflow uses `CreateVideo` followed by `SaveVideo`.

Implement a streaming video writer that receives completed frames incrementally and encodes them without accumulating the entire generated video.

Use FFmpeg or PyAV.

Requirements:
- Configurable output FPS.
- Configurable video codec.
- H.264 output initially.
- Preserve source audio when requested.
- Support long videos.
- Release completed frames promptly.
- Handle interruptions and failed encoding cleanly.

### Problem D: WanAnimate2Stream is currently only an adapter

The current `WanAnimate2Stream` delegates to the native `WanAnimate2ToVideo` node.

This preserves conditioning behavior but does not itself implement window-by-window execution.

Implement a controller that coordinates:

1. Loading a bounded driver-video window.
2. Preparing Wan Animate 2 conditioning.
3. Running the existing sampler.
4. Decoding the generated latent.
5. Writing completed output frames.
6. Releasing window-specific tensors.
7. Advancing to the next window.

Preserve the native model and sampler logic wherever possible.

**Important:** A ComfyUI node that outputs one full IMAGE tensor is not a complete streaming solution.

Design the execution controller so each window is processed and released before the next window is decoded.

If ComfyUI's standard graph execution model prevents true streaming between nodes, implement a custom orchestration node or an external controller using the ComfyUI API.

Do not introduce a fake streaming abstraction that still accumulates the complete video.

## 7. Memory Requirements

The target is bounded memory usage.

Memory should depend primarily on:

- Active input window size.
- Processing resolution.
- Model weights.
- Sampling workspace.
- Active VAE decode tiles.
- Encoder buffers.

Memory should not increase continuously as the video duration increases.

### Resolution handling

Support input resolutions including:

- 480p
- 720p
- 1080p

Allow input resolution to differ from generation resolution.

For example:

```text
Driver input: 1920×1080
Generation: 480×832
Output: 480×832
```

Resize frames during or immediately after decoding, before accumulating a window-sized tensor.

Do not decode and store the entire original-resolution video before resizing.

**Important:** Supporting a 1080p input video does not imply that Wan Animate 2 can generate native 1080p output within 32 GB VRAM.

The implementation must clearly distinguish input resolution, model generation resolution, and encoded output resolution.

## 8. Quality and Continuity Requirements

Streaming must not change the mathematical behavior of a single Wan Animate 2 inference window.

Preserve:

- Reference-image conditioning.
- Pose-video conditioning.
- CLIP vision conditioning.
- Positive and negative prompts.
- Native sampler behavior.
- Temporal context.
- Existing LoRA.
- Existing VAE.

Window transitions must avoid:

- Duplicate frames.
- Missing frames.
- Visible jumps.
- Incorrect temporal offsets.
- Character identity changes caused by incorrect continuation state.

Document any unavoidable quality trade-offs when processing long videos in separate windows.
